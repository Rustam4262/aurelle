# PM2 Cluster Mode — AURELLE

## Overview

AURELLE runs under PM2 in **cluster mode** (`instances: "max"`), spawning one worker
per CPU core. All cluster-safety issues — sessions, rate limiting, WebSocket, and cron
jobs — are addressed without any breaking changes for single-process deployments.

---

## Configuration

File: `ecosystem.config.cjs`

```js
{
  name: "aurelle-production",
  script: "dist/index.cjs",
  instances: "max",       // one worker per CPU core
  exec_mode: "cluster",
  wait_ready: true,       // wait for process.send('ready') before routing traffic
  listen_timeout: 10000,  // ms to wait for ready signal
  kill_timeout: 5000,     // ms to wait for graceful SIGTERM drain
  max_memory_restart: "1G",
}
```

The app sends `process.send('ready')` inside the `listen()` callback, after Redis and
WebSocket pub/sub are fully initialised.

## Cluster-Safety Matrix

| Concern | Solution | Requires Redis |
|---|---|---|
| **Sessions** | `connect-redis` RedisStore (P2.1) | Yes |
| **Rate limiting** | `rate-limit-redis` shared counters (P2.2) | Yes |
| **WS auth tokens** | Stored in Redis (`aurelle:wstoken:*`) | Yes |
| **WS broadcasts** | Redis pub/sub (`aurelle:ws:broadcast`) | Yes |
| **Cron jobs** | Run only on `NODE_APP_INSTANCE=0` | No |
| **Dashboard cache** | Redis cache (P2.3) | Yes |

**Without Redis** (`REDIS_URL` absent): runs as a single process or fork mode — all features
fall back to in-memory, which is correct. Do not use cluster mode without Redis.

## WebSocket in Cluster Mode

### Problem

Without cluster-safety, two failures occur with N workers:

1. **Token mismatch** — Token is generated by Worker A (HTTP), but the WS upgrade
   lands on Worker B (different TCP connection). Worker B's in-memory Map doesn't
   have the token → `4001 Invalid or expired token`.

2. **Broadcast miss** — A booking is confirmed by Worker C's handler, which calls
   `broadcast("user_42", ...)`. Only clients connected to Worker C receive the event.
   The user's WS connection is on Worker D → no notification.

### Solution

**Tokens** — `createWsToken()` writes to Redis (`aurelle:wstoken:<hex>`, TTL 31s).
`consumeWsToken()` uses atomic `getDel` — guaranteed one-time use, any worker can
consume the token.

**Broadcasts** — `broadcast(room, event, data)` publishes to the Redis channel
`aurelle:ws:broadcast`. Each worker subscribes to this channel via a **dedicated
subscriber connection** (subscribe mode is exclusive — requires a separate client).
Every worker's subscriber calls `broadcastLocal()` → delivers to local room members.

```
Worker A (HTTP handler)
  └─ broadcast("user_42", "booking_confirmed", {...})
       └─ client.publish("aurelle:ws:broadcast", JSON.stringify({room, event, data}))

Redis pub/sub channel: aurelle:ws:broadcast
  ├─ Worker A subscriber → broadcastLocal("user_42", ...) [if user_42 connected here]
  ├─ Worker B subscriber → broadcastLocal("user_42", ...) ← user_42's WS is here ✓
  ├─ Worker C subscriber → broadcastLocal("user_42", ...) [no-op, no members]
  └─ Worker D subscriber → broadcastLocal("user_42", ...) [no-op, no members]
```

**Fallback** (no Redis): `broadcast()` falls back to `broadcastLocal()` — correct
behaviour for single-process or development mode.

### Redis key namespacing

```
aurelle:wstoken:<48-hex-chars>   TTL 31s  (one-time auth tokens)
aurelle:ws:broadcast             pub/sub channel (no stored keys)
```

## Cron Jobs

Both cron jobs run **only on `NODE_APP_INSTANCE === "0"`** (the first worker PM2
assigns). All other workers skip them and log `[Cron] Jobs skipped (instance N)`.

This is checked in `server/index.ts` inside the `listen()` callback:

```typescript
const isMainInstance =
  !process.env.NODE_APP_INSTANCE || process.env.NODE_APP_INSTANCE === "0";

if (isMainInstance) {
  startSanctionExpiryJob();
  startBookingRemindersJob();
}
```

`NODE_APP_INSTANCE` is injected automatically by PM2 for each cluster worker (0, 1, 2…).
In development/single-process it is absent → `isMainInstance = true` → jobs run normally.

## Graceful Shutdown

PM2 sends `SIGTERM` when reloading or stopping. Node.js `http.Server` finishes in-flight
requests before closing. WS connections are dropped after `kill_timeout` (5s).

The app signals readiness with `process.send('ready')` inside `listen()`, after:
- Redis session store connected (or fell back to PgSession)
- WebSocket pub/sub subscriber connected (or fell back to local mode)
- HTTP server is accepting connections

PM2's `wait_ready: true` + `listen_timeout: 10000` means PM2 waits up to 10s for the
ready signal before marking the process as online and routing traffic to it.

**Zero-downtime reload** (`pm2 reload aurelle-production`):
1. PM2 starts a new worker, waits for `ready`
2. Once new worker is ready, old worker receives SIGTERM
3. Old worker drains in-flight requests (up to `kill_timeout`)
4. PM2 repeats for each worker sequentially → no downtime

## Deploy

### First-time start (server not yet running)

```bash
cd /var/www/aurelle
git pull origin main
npm install
npm run build
pm2 start ecosystem.config.cjs --env production
pm2 save
pm2 startup   # configure PM2 to survive reboots
```

### Rolling reload (code update, no downtime)

```bash
cd /var/www/aurelle
git pull origin main
npm install
npm run build
pm2 reload aurelle-production
```

### Check status

```bash
pm2 status
pm2 logs aurelle-production --lines 50
pm2 monit   # live CPU/memory per worker
```

## Load Test

Install `autocannon` once:

```bash
npm install -g autocannon
```

Basic throughput test (2 minutes, 50 concurrent connections):

```bash
autocannon -c 50 -d 120 https://aurelle.uz/api/health
```

Auth-requiring endpoint (replace SESSION_COOKIE with a real session):

```bash
autocannon -c 20 -d 60 \
  -H "Cookie: aurelle.sid=<your-session>" \
  https://aurelle.uz/api/admin/dashboard
```

Expected results with 4 workers and Redis:
- `/api/health` — 2 000+ req/s, p99 < 20ms
- `/api/admin/dashboard` (cache warm) — 500+ req/s, p99 < 50ms

## Observability

Check which worker is serving requests (logged per request in production):

```bash
pm2 logs aurelle-production --lines 100 | grep "instance"
```

Monitor Redis pub/sub activity:

```bash
redis-cli -u $REDIS_URL monitor | grep "aurelle:ws"
```

Check WS token keys (should all have short TTLs):

```bash
redis-cli -u $REDIS_URL --scan --pattern 'aurelle:wstoken:*'
```
